# Implementation and population plan

This plan adds community discovery to the original framework. The user created `xulfr/om-firmware-atlas` and authorised bootstrap pushes to main; branch protection follows setup.

## Initial delivery

- Entry contract, shared Claude pointer, three short roles and source/status/freshness workflows.
- Seven record types: the original six plus community venues, with schemas and scoped-reference checks.
- A bounded initial corpus spanning the two OM-5 generations, OM-3, E-P7, PEN-F and an E-M10 IV discovery route.
- Small shared guides that route into existing technical homes rather than mirror their notebooks.
- Generated camera/project/evidence/source/community pages and agent route shards with reading costs.
- Fixed routing cases, semantic/generator regression tests, strict site build and read-only PR validation.
- GitHub Pages from main, with source revision/build time and a prominent community directory linking r/M43 and the confirmed published Discord invite.

The OM-5 evidence slice retains a named-package failure, restoration from that incident, an incomplete positive Mark II report and bounded emulator tracing. This validates distinctions before expanding the catalogue.

## After bootstrap

1. Main is protected with required PRs, passing **Atlas validation**, an up-to-date branch and resolved conversations. Maintainers can review and merge their own PRs without a separate approval. Contributors use normal GitHub permissions and their own commit identities; there is no custom author/authentication gate.
2. Give ordinary agents a new source URL and exercise the PR workflow. The CLI routing tests are deterministic checks, not proof of external client compliance.
3. Deepen OM-3/E-P7 feature-level evidence and interface records, including minimum-release semantics and unsupported exports. Do not infer a shared-panel agreement.
4. Add exact input hashes for the firmware entries that currently record version/build only. Review individual db firmware camera reports before promoting its release-level claims.
5. Add other body projects from the upstream discovery lists through bounded source PRs. Expand research/tool profiles when an actual task needs them.
6. Add community venues or more precise public channel links as the community supplies them. Record listing basis, access and link-check scope; preserve technical findings through specific posts/messages and their publication permission.

Weekly CI produces a source/freshness report and republishes the existing main content. It does not call an LLM, crawl private chats, change canonical claims or raise unsolicited upstream messages. A maintainer can hand a queue item to an agent. Automatically invoking a separate agent service is a later operational choice.

Success means a source can become scoped evidence, useful routes and human pages through a reviewable PR. An exhaustive camera database, symbol index or new shared firmware toolchain is outside this initial delivery.
